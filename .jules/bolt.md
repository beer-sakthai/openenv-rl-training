## 2024-08-21 - [Fast path short-circuits to reduce execution time during regex checks and text analysis]
**Learning:** Checking for `<tool_call>` existence directly using string matching `in` is extremely fast compared to executing the compiled regex when `<tool_call>` evaluates to `False`. The length validation of the `raw` text can also skip string copies completely. Most surprisingly, Python's `Counter(s).values()` takes disproportionately long for huge repetitive sequences compared to `s.count()`. The Pigeonhole Principle optimization (sampling strings at l//4, l//2, 3*l//4) outperforms `max(collections.Counter(s).values())` by over 90% for large sets where a single character dominates.
**Action:** When a function runs recursively over large lists mapping regex, short-circuit validation checks upfront to save processing time on inputs that won't match anyway. Look for opportunities to evaluate string logic independently without relying on python data-structure allocations (`Counter`, `dict()`).
## 2026-08-21 - [String Concatenation in Eval Render Loops]
**Learning:** Found a codebase-specific anti-pattern in `eval_hermes_env.py` and `eval_bench_peft.py` where string concatenation (`+=`) was used inside loops to render the `tool_calls` list for every turn of agentic evaluation. Given the recursive and multi-turn nature of evaluation scripts, doing heavy string re-allocation overheads can silently degrade evaluation speed across thousands of turns. A similar anti-pattern existed in `openenv-custom-training/train.py` where `append()` in a loop was used instead of a list comprehension for reward parsing.
**Action:** Always replace `+=` inside rendering loops with a `list` accumulator and `"\n".join(parts)`. Replace loop-based list building with list comprehensions where possible (e.g. `_browsergym_reward`).
